**Scope:** Full-site audit (code-based static analysis of the production Next.js source in `bjosh12/dnv`)
**Date:** 2026-07-23
**Method:** LLM-first source review against `resources/references/llm-audit-rubric.md`. Live-URL evidence (rendered HTML, PageSpeed/CWV, security headers, robots/llms.txt fetch) could **not** be collected — see [Environment Limitations](#environment-limitations). All findings below are derived directly from the application source (`app/`, `components/`, `lib/`), which is the ground truth for what ships to production, so confidence is high on everything that doesn't require a live network request.

## Environment Limitations (Update: partially resolved)

Outbound HTTPS to `digitalnomadinspain.com` from this session's general network path (direct `curl`, the `WebFetch` tool) is **still** blocked (403 on CONNECT) — that part of the environment's network policy hasn't changed. However, once the Vercel MCP integration was connected to the account that actually owns the `dnv` project, its `web_fetch_vercel_url` tool successfully fetched the live production site (`https://www.digitalnomadinspain.com`), several individual pages, `robots.txt`, and `sitemap.xml`, including full response headers. That data is now used below and supersedes the equivalent `Hypothesis`/`Info` items from the original code-only pass — those items are marked "Confirmed live" where upgraded. The skill's bundled Python scripts (`pagespeed.py`, `security_headers.py`, `robots_checker.py`, etc.) still can't run directly, since they use `requests` over the still-blocked general network path — but the same checks were performed manually via the Vercel fetch tool instead. **Still not verified:** actual PageSpeed/CrUX Core Web Vitals (requires Google's PSI API, not reachable), rendered-DOM visual/screenshot analysis, and broken-link crawling beyond the pages spot-checked below.

## Audit Summary

**Overall Score: 65/100 — Needs Improvement** (Score confidence: High on everything below marked "Confirmed live"; Medium on code-only items)

**Top 3 issues:**
1. `/contact` is a client component with **no metadata export at all** — confirmed live: the rendered page's `<title>` and meta description are byte-identical to the homepage's, and it has no canonical tag, on a page that's also listed in the live `sitemap.xml`. *(Confirmed live)*
2. Structured data coverage for blog posts is **inconsistent**: a live Sanity-authored post (`/blog/tie-fingerprinting-appointment-spain`) correctly ships `BlogPosting` JSON-LD, but a live BabyLoveGrowth-sourced post (`/blog/spanish-administration`) ships **no article-level schema at all** — confirmed by grepping the full rendered HTML (including the RSC hydration payload) for `BlogPosting`/`FAQPage` and finding zero matches. Roughly 28 of the site's ~30 indexed URLs are blog posts, so this gap likely affects a large share of the content. *(Confirmed live — supersedes the original report's "Likely" concern about `FAQPage` misuse, which was not observed in either live sample checked)*
3. All Sanity-CDN and testimonial-avatar images render through raw `<img>` tags instead of `next/image`, because `cdn.sanity.io` is missing from `next.config.ts`'s `images.remotePatterns`. *(Confirmed in source; live homepage HTML shows the hero image correctly served through `/_next/image` with a full responsive `srcset`, while every Sanity/Unsplash-sourced card image on the same page has no `srcset` and no `width`/`height` attributes — confirmed live)*

**Top 3 opportunities:**
1. Add the missing `/services` hub page to `sitemap.ts` — confirmed absent from both the source `STATIC_PATHS` array and the live `sitemap.xml` output, despite being a real, unique, nav-linked page.
2. Add `sameAs` links to the sitewide `ProfessionalService` JSON-LD (confirmed still `[]` in the live homepage's schema) — the social profiles already exist in `lib/constants.ts` (`SOCIAL_LINKS`) but are never wired in.
3. Add `BreadcrumbList` structured data to service and blog pages — confirmed absent from every live page checked.

### What live access resolved from the original report
- **Apex → www redirect: now Confirmed Pass.** `https://digitalnomadinspain.com/` returns a live `308 Permanent Redirect` to `https://www.digitalnomadinspain.com/`, matching `SITE_URL` in `lib/constants.ts`. (Previously listed as `Hypothesis`.)
- **Security headers: now Confirmed Pass.** Live response headers for `www.digitalnomadinspain.com` exactly match `next.config.ts`'s `securityHeaders` array (`x-content-type-options: nosniff`, `referrer-policy: strict-origin-when-cross-origin`, `permissions-policy: camera=(), microphone=(), geolocation=()`) — and `x-frame-options`/`content-security-policy` are confirmed absent in production, matching the documented intentional trade-off for the Sanity Presentation tool.
- **`robots.txt`: Confirmed Pass**, live content is byte-identical to what `app/robots.ts` generates.
- **`llms.txt`: Confirmed 404** (upgraded from `Info`/unchecked to `Confirmed` — the file genuinely doesn't exist in production).
- **`/services` missing from the sitemap: Confirmed**, both in source and in the live `sitemap.xml` (29 URLs listed, `/services` is not among them).

2. A full census of `faqJsonLd.@type` across all ~28 blog posts — only 2 were spot-checked live; one had no schema at all, the other had `BlogPosting` with no `FAQPage`. Worth checking a larger sample before fully ruling out `FAQPage` misuse on any BLG-sourced post.
3. Visual/rendered-DOM analysis (screenshots, above-the-fold, responsive layout) — not attempted this pass; would need `capture_screenshot.py`/`analyze_visual.py` with Playwright against a reachable URL.
4. Broken-link crawl beyond the pages spot-checked (homepage, `/contact`, 2 blog posts) — `scripts/broken_links.py` needs general network access, still blocked.
